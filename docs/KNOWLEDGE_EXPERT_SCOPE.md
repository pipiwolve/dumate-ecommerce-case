# 内部知识库与专家范围

## 三层职责

本案例把“专家能力”拆成三类资产，避免把一段 Prompt 误认为真实专家：

1. `skills/ecommerce-delivery-review/SKILL.md` 是审查编排规则，负责收集 GitHub
   证据、识别风险、检索知识、匹配专家并生成双角色报告。
2. `knowledge/published/` 是带版本、权限、来源和内容锚点的领域知识。
3. `knowledge/experts.json` 是人员专家目录，记录领域、负责模块、可用状态、联系入口
   与升级条件。本案例中的姓名和联系方式均为模拟数据。

## 当前知识覆盖

| 知识主题 | 主要判断 | 权限 |
|---|---|---|
| 库存预占并发一致性 | 原子边界、check-then-act、订单幂等、并发验收 | 工程、交付 |
| 2025 超卖事故复盘 | 历史症状、根因、缓存放大与整改项 | 仅工程 |
| 购物车性能基线 | N+1、批量查询、查询预算与 P95 目标 | 工程、交付 |
| 后台库存安全 | RBAC、调整原因、审计字段与二次审批 | 工程、交付 |
| 促销发布门禁 | P0 阻塞、升级路径与客户通知原则 | 工程、交付、客户项目经理 |

客户项目经理只能读取 `public` 知识；内部与受限材料只能转化为经过脱敏的风险结论，
不能直接进入客户报告。

## 明确边界

当前一期不覆盖支付风控、推荐算法、物流履约、财务对账、数据隐私合规、云基础设施
容量和通用语言级代码审查。若风险标签超出上述范围，MCP 应返回“无高置信度专家”，
不能编造匹配结果。正式上线时应接入企业 SSO/通讯录、真实排班、文档审批与权限系统。

## 扩展方式

新增领域时先沉淀经过负责人审核的知识文档，再扩展专家目录和匹配标签，最后更新
审查 Skill 的触发条件与报告脱敏规则。GitHub 热门 Skill 可以作为方法参考，但不能
直接充当企业知识或人员专家；外部内容必须完成来源、版本、安全和适用性评审。
